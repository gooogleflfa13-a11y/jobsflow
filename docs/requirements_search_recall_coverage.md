# JobsFlow 检索召回与漏扫控制技术手册

版本：v1.0
日期：2026-08-04
状态：技术要求与实现方案（本手册本身不代表已完成代码实现）

## 1. 目标

本手册针对 JobsFlow 在招聘门户检索阶段可能出现的“漏扫”问题，定义可实现、可测量、可回退的改进方案。

目标不是抓取全网所有职位，而是：

> 在用户明确的职位、行业、地点、薪资和其他限制范围内，尽可能找全值得人工查看的职位，同时控制噪声、网络请求、门户压力和模型成本。

本手册只处理“岗位是否进入系统”及其可观测性，不改变以下既有原则：

- 用户仍然需要查看和选择值得投递的 JD；
- 不自动生成所有岗位的 CV 或 Cover Letter；
- 不自动提交申请；
- 用户画像的事实基线与能力上沿仍然分离；
- 法律/合规不作为任何行业的内置默认；
- 产品线与个人求职 workspace 保持隔离。

## 2. 问题定义：什么叫“漏扫”

不能把所有未进入最终候选表的岗位都称为漏扫。系统必须区分以下状态：

```text
门户有岗位
   ├─ 未被门户查询返回       = retrieval_miss（检索漏扫）
   ├─ 已返回但超过时间窗口   = rejected_recency
   ├─ 已返回但超出用户范围   = filtered_scope
   ├─ 已返回但被错误去重     = dedupe_miss
   ├─ 已返回但 JD 不完整      = shallow_jd
   └─ 已返回且进入评分       = retrieved
```

本项目重点降低 `retrieval_miss`，同时保留足够日志识别 `filtered_scope`、`dedupe_miss` 和 `shallow_jd`，避免把过滤结果误认为检索失败。

### 2.1 召回率分层

必须分别计算：

1. **网络检索召回率**：目标范围内的职位有多少被门户查询带回系统。
2. **入站匹配召回率**：已经带回系统的职位中，有多少被用户画像和评分器识别为相关。
3. **JD 可用率**：带回的职位中，有多少拥有足够完整的 JD 可供深度判断。

用户画像、事实基线和能力上沿主要提升第 2 项；本手册主要提升第 1 项，并监控第 3 项。

## 3. 总体架构

```text
简历事实 + 已确认求职意向
              │
              ▼
       Query Planner（查询规划器）
              │
       查询词族 + 查询预算 + 门户策略
              │
       ┌──────┼─────────┐
       ▼      ▼         ▼
   LinkedIn  JobsDB  CTgoodjobs
   worker    worker   worker
   内部串行  内部串行  内部串行
       └──────┼─────────┘
              ▼
       标准化、去重、时间过滤
              │
              ├─ Retrieval Audit
              ├─ 初评与硬规则
              └─ 现有两段评分和深 JD
```

三个门户可以并行；同一门户的查询和分页必须串行，并继续遵守该门户的间隔和失败退避策略。

## 4. 查询规划器（Query Planner）

### 4.1 输入

查询规划器只能读取以下已授权资料：

- 用户已确认的简历事实；
- 用户已确认的求职意向；
- 地点、薪资、语言、工作权和其他限制；
- 用户选择的画像上沿幅度；
- 行业快速研究结果（如存在可靠来源）；
- 用户通过 `/intent add` 或 `/intent replace` 确认的增量意向。

普通聊天中未经确认的想法不得直接改变检索范围。

### 4.2 查询词族

每个岗位方向至少可以生成以下查询族，但不要求每族都执行：

| 查询族 | 作用 | 示例（仅示意） |
|---|---|---|
| `core_title` | 用户明确想找的职位名 | Operations Analyst |
| `title_synonym` | 同职位不同命名 | Business Operations |
| `responsibility` | JD 常用职责表达 | process improvement、monitoring |
| `skill_tool` | 工具、方法和技能 | SQL、workflow、reporting |
| `industry` | 行业表达 | fintech、SaaS、payments |
| `business_context` | 业务场景 | cross-border、platform operations |
| `adjacent_role` | 用户允许的相邻方向 | Risk Operations、Client Operations |

查询词必须保存来源和理由，不能只保存一串无法解释的关键词。

### 4.3 查询词约束

查询规划器必须：

- 去除空词、重复词和明显无意义的泛词；
- 标记每个词属于核心、相邻还是探索范围；
- 不把能力上沿直接写成用户已经做过的经历；
- 不自动加入用户未授权的地点、行业或薪资假设；
- 不使用法律/合规作为跨行业默认词库；
- 在模型输出不完整时使用确定性词族模板回退。

### 4.4 低能力模型契约

大模型只负责提出候选查询词，不负责直接执行门户搜索。模型输出必须符合机器可读结构：

```json
{
  "direction": "A",
  "families": [
    {
      "family": "core_title",
      "terms": ["Operations Analyst", "Business Operations Analyst"],
      "scope": "core",
      "reason": "来自用户已确认的目标职位"
    }
  ]
}
```

程序必须校验结构、范围、重复、词数和空值。校验失败时使用上一次已确认配置或行业中性的确定性回退，不得因为模型没有理解而静默减少查询范围。

## 5. 门户专用适配器

统一查询词族不能原样发送到所有门户。每个门户适配器负责：

- 将查询族转换为门户支持的参数；
- 选择地点和时间窗口；
- 设置页码和每页限制；
- 执行门户特定的重试和退避；
- 记录门户原始查询与规范化后的查询；
- 保持该门户内部串行。

### 5.1 LinkedIn

- 组合职位词、技能/职责词和地点；
- 需要识别 date-only 发布日期，不把当天岗位错误判定为超出临时窗口；
- 对同一查询允许有限分页；
- 复用 worker 进程中的网络/DNS缓存；
- 不因为单个查询失败而丢弃同一 worker 已完成的其他查询结果。

### 5.2 JobsDB

- 优先使用职位词、职责词和行业词的组合；
- 使用门户支持的日期范围，同时保留本地时间过滤；
- 对每页结果执行规范化和去重；
- teaser 岗位进入系统后必须标记 JD 深度，不得当作完整 JD。

### 5.3 CTgoodjobs

- 使用已复用的 session headers；
- 查询和分页保持门户内串行；
- 保留 API 返回的结构化字段和 teaser；
- session、400、限流或验证码错误必须单独记录；
- 不因为检索阶段结果较浅而覆盖用户已粘贴的完整 JD；
- CapSolver 等外部方案只能由用户自行配置，不能写入公共默认配置。

## 6. 有限分页与自适应停止

### 6.1 基本规则

每个查询必须有明确的 `page_budget`，不能无限分页。建议初始策略：

```text
精准模式：每个查询最多 1 页
平衡模式：核心查询最多 2 页，相邻查询最多 1 页
广覆盖模式：核心查询最多 3 页，其他查询最多 2 页
```

最终数值必须通过实际数据校准，不能把示例数值当成永久常量。

### 6.2 停止条件

继续下一页前检查：

- 上一页是否产生了新的规范化 URL；
- 新岗位比例是否高于最低阈值；
- 与已有查询的重复率是否过高；
- 是否达到本次扫描的请求预算；
- 门户是否出现限流或异常。

满足以下任一条件即可停止该查询：

- 达到 `page_budget`；
- 连续一页没有新岗位；
- 新岗位比例低于配置阈值；
- 门户错误达到该查询的重试上限；
- 剩余时间/网络预算不足。

## 7. 去重与过滤顺序

为了避免“搜到了但被错误丢掉”，处理顺序必须固定：

```text
门户原始结果
   ↓
字段规范化和 URL 清理
   ↓
记录 retrieval observation
   ↓
URL / job id / company-title 去重
   ↓
时间窗口过滤
   ↓
用户范围规则
   ↓
评分和深 JD
```

过滤后的岗位不能从审计记录中消失。每个岗位应保留最终状态和原因，例如：

```json
{
  "retrieval_state": "retrieved",
  "decision": "reject",
  "reject_reason": "outside_configured_search_scope",
  "query_ids": ["A-core-01", "A-duty-02"]
}
```

同一职位被多个查询找到时，必须保留全部 `query_ids`，以便判断查询族的边际贡献。

## 8. 检索审计指标

每次扫描的 `_run.json` 应增加或保持以下指标：

### 8.1 查询级指标

- `portal`；
- `query_id`；
- `query_family`；
- `page`；
- `term` 或门户规范化查询；
- `raw_count`；
- `normalized_count`；
- `new_unique_count`；
- `duplicate_count`；
- `filtered_count`；
- `duration_ms`；
- `retry_count`；
- `error`。

### 8.2 扫描级指标

- 三门户各自的总结果数；
- 三门户各自的新岗位数；
- 查询族的独立贡献；
- 分页触发次数；
- JD 缓存命中率；
- 检索错误数；
- `retrieval_miss` 无法直接观测时，记录为“未能验证”，不得伪造为零漏扫。

## 9. 召回率验收方法

没有人工确认的目标集合，就不能证明召回率提升。验收需要建立一个小型 gold set：

1. 用户从门户手工挑选 30–50 个明确符合范围的岗位；
2. 记录岗位 URL、标题、门户、发布时间和用户认为的方向；
3. 清空或隔离对应扫描结果；
4. 运行不同查询模式；
5. 检查岗位是否被抓入系统；
6. 再检查是否被正确识别为相关。

至少分别计算：

```text
检索召回率 = 被系统抓到的 gold set 岗位数 / gold set 总数
入站匹配召回率 = 被识别为相关的 gold set 岗位数 / 已抓到的 gold set 岗位数
```

同时记录：

- 每增加一个查询带来的新岗位数；
- 噪声岗位比例；
- 单个新岗位消耗的网络请求数；
- 扫描耗时变化。

## 10. 能耗、网络和模型约束

### 10.1 网络

- 三门户可以并行；
- 同一门户必须串行；
- 使用已有 URL-keyed JD cache；
- 查询和分页共用请求预算；
- 失败重试必须有上限；
- 单门户异常不得阻塞其他门户的结果写入。

### 10.2 大模型

- 不在每个门户查询前调用大模型；
- 大模型只在 `/setup` 或 `/intent confirm` 阶段生成候选查询词；
- 扫描阶段使用确定性程序执行已确认计划；
- 模型输出必须经过 schema、范围和词数校验；
- 弱模型失败时回退到上一次确认配置；
- 不允许模型静默删除用户已确认的查询族。

### 10.3 用户选择

默认使用“平衡模式”。只有用户明确选择广覆盖时，才增加查询族、分页和门户预算。扩展召回不应自动改变用户画像或放宽硬性限制。

## 11. 与现有模块的边界

本需求可以影响：

- `tools/fresh_24h/fresh_24h_scan.py`；
- `tools/fresh_24h/queries.json` 及其私有迁移；
- `/setup`、`/intent` 的查询配置生成；
- 三个门户 CLI 的批量请求和分页参数；
- `_run.json` 检索审计字段；
- 相关单元测试和回放测试。

本需求暂不改变：

- `two_pass_score.py` 的六维评分维度；初评调度、扫描深度和最终保留偏好由评分召回与成本控制策略单独管理；
- 用户画像的事实基线/能力上沿规则；
- CV、Cover Letter 和 PDF 生成；
- `/apply` 的人工确认原则；
- Google Sheets 的列结构；
- 产品线与个人求职 workspace 的隐私边界。

## 12. 实施阶段

### Phase 0：可观测性

- 扩展 query/page 级日志；
- 固化 retrieval state；
- 建立 30–50 个岗位的 gold set；
- 记录当前基线耗时、请求数和检索召回率。

### Phase 1：低风险召回增强

- 增加查询词族 schema；
- 增加门户专用查询转换；
- 支持有限分页；
- 保持默认平衡模式；
- 添加回归测试和离线回放测试。

### Phase 2：自适应查询预算

- 根据新岗位数和重复率停止分页；
- 将预算优先给边际贡献高的查询族；
- 对连续零结果或高重复查询降权；
- 将结果呈现给用户，而不是静默改变意向。

### Phase 3：反馈闭环

- 收集用户“漏掉的好岗位”反馈；
- 记录投递、面试、拒绝和无回复；
- 生成查询/意向调整建议；
- 只有用户确认后才更新私有检索配置。

## 13. 验收标准

实现后至少满足：

- 三门户仍然并行，单一门户内部查询和分页仍然串行；
- 现有 `/scan`、`/scan temp`、`/scan daily` 入口不变；
- 查询词族来源可追溯，模型失败不会静默缩小查询范围；
- 每个查询和分页都有审计记录；
- 已返回但被过滤的岗位仍可在运行记录中解释；
- URL、job id 和公司-职位去重结果稳定；
- 用户粘贴的完整 JD 不会被检索或 enrich 流程覆盖；
- 现有评分、材料和隐私边界回归测试通过；
- gold set 上的检索召回率、噪声比例、耗时和网络请求数均有前后对比；
- 未经用户确认，不改变意向、行业边界、硬性限制或个人 workspace。

## 14. 不采用的方案

以下方案不作为默认实现：

- 无限增加关键词；
- 对每个查询都调用大模型；
- 不受控制地抓取全网；
- 三门户内部无限并发；
- 将能力上沿直接写成工作经历；
- 为了召回率自动放宽用户的薪资、地点或工作权限制；
- 用一次扫描结果静默修改用户画像；
- 以“抓到更多岗位”替代“抓到更多值得查看的岗位”。

## 15. 最终判断

这项改造不需要推翻现有 JobsFlow 架构。现有用户画像和能力上沿继续负责“岗位进入系统后的语义判断”；本手册新增的查询词族、门户适配、有限分页和检索审计负责“让更多合适岗位有机会进入系统”。

二者组合后，系统才形成完整的召回链路：

```text
意向理解 → 查询覆盖 → 门户检索 → 去重审计 → 语义匹配 → 人工确认
```

最终效果必须以 gold set 和运行指标验证，不能仅凭扫描结果数量或模型主观判断“没有漏扫”。
